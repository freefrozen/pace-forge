# 复核 `segment_json.avgStep`：段步数还是步频

issue #12 的追加给出一条 7.4.01 反编译链：

```java
int i8 = (int) (((long) (i * 60)) / j);  // i = 段步数，j = 段秒数
analysisStateBean.OooO(i8);              // setter 写 avgStep
analysisStateDB.setAvgStep((int) analysisStateBean.OooO0O0());
```

按这条链，本地分析状态里的 `avgStep` 是**换算后的步频（步/分钟）**。本轮用真机样本
反查了我们发出的那层 `segment_json`，结论如下。

## 两种解释对照

- **按步频读**：20 秒段 78 步 → 234 步/分，81 步 → 243 步/分。竞走世界纪录也就 200 出头，
  这个量级和同一份样本里 `avgStepFreq≈173.8` 对不上，也不是人跑得出来的曲线。
- **按段步数读**：1984 步 / 1683.84 米 = 1.18 步/米，步幅约 0.85 米；整体 212 步/分，
  和 `avgStepFreq` 的 173.8 有点差，但首段是 86 秒 15 步的 GPS 漂移段，把它剔掉之后
  （1969 步 / 475 秒）约 249 步/分，仍偏高——说明这份样本的步数本身不是严格按真实步频
  算的，或者 `totalSteps` 另有来历。

## 结论

1. **OBS `segment_json.avgStep` 是段步数**，依据是「步频解释会得到 234~243 步/分的
   非人类量级」和「Σ段 = 1984 = 报文总步数」这两条硬事实。本实现（`build_segments_from_points`
   按里程比例分摊 `total_steps`、`avgStep == originAvgStep`）与之相符。
2. 7.4.01 那条 bean 链写的是**本地分析状态 / 数据库里的 `avgStep`**，与上传对象里同名
   字段不是同一层。中间是否还有一次「步频 → 段步数」的换算，没找到转换点，列为
   **未确认**——不拿「公式输入是步数」反推「OBS 字段也是步数」，也不拿相反方向硬套。
3. 7.4.02 是否改过这个字段语义，没有样本，不做推断。
4. 样本口径：单机单次、未知客户端版本；「步频解释不成立」在这份样本上是确定的，
   「所有版本都一样」不是。

## 对实现的处置

本轮**不改** `avgStep` 的写入方式：现有实现与真机 OBS 对象一致，且属于校准数值范畴
（`avgStep` 参与段表审核与配速曲线）。要改得先有「数据库值 → 上传值」的转换证据。
